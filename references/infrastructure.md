# Работа с публичной инфраструктурой

## URL и источники

Разбирай ссылку локально библиотекой URL. Сохраняй точный хост и, для международного доменного имени, его Unicode- и ASCII-представления. Не определяй регистрируемый домен простым отбрасыванием всех частей кроме двух: используй достоверные сведения о публичных суффиксах либо RDAP самого домена. Нормализованная запись нужна для сопоставления; оригинал остаётся локально.

Не используй строковую подстановку непроверенного ввода в shell-команды. Для HTTP-запроса к сервису кодируй параметры штатной библиотекой. Сеть используй для получения сведений у источников, а не для контакта с подозрительной страницей.

У исходной страницы может быть значимый путь. Отчёт о корне сайта не заменяет отчёт об исходном URL. Сверяй URL, дату, конечную страницу и среду наблюдения сохранённого отчёта. Результат одного наблюдения описывает именно это наблюдение.

## DNS и регистрация

| Сведения | Что фиксировать | Предел вывода |
|---|---|---|
| A / AAAA | Имя, тип записи, ответ, TTL, резолвер, время UTC | Адрес, полученный в данном запросе |
| NS | Ответ DNS, цепочку делегирования при наличии данных | Инфраструктура DNS; не личность владельца сайта |
| NXDOMAIN, SERVFAIL, timeout | Точный статус и источник | Ошибка или отсутствие записи при проверке; не причина исчезновения сайта |
| RDAP домена | Источник, события, статусы, регистратор | Значения полей реестра; дата сертификата не заменяет дату регистрации |
| RDAP IP / RIR | Диапазон, организация ресурса, ASN, abuse-контакт | Сведения о сетевом ресурсе; не доказательство владельца страницы |
| IP-геолокация | Провайдер базы, дата, результат | Оценка базы данных; не местонахождение человека |

В PowerShell при наличии `Resolve-DnsName` можно выполнить `Resolve-DnsName -Name example.com -Type A` и отдельный запрос NS. `example.com` — учебный домен, не индикатор. В Git Bash сначала проверь наличие нужной команды. Выходы разных оболочек не смешивай.

Для RDAP используй официальный сервер соответствующего реестра/RIR либо проверенный механизм обнаружения сервера. Сохраняй первичный JSON. Сайт агрегатора помогает найти запись, но фактического провайдера обращения проверяй по первичному источнику.

Не угадывай контакты вида `abuse@...` или `security@...`. Записывай найденный официальный адрес/форму, роль получателя, ссылку на источник и дату проверки.

## Исторические сведения и сертификаты

Исторический DNS показывает наблюдавшиеся соответствия имени и адреса. Для каждой связи укажи первую/последнюю дату, если источник их предоставляет. Отсутствие записи означает отсутствие данных в этом источнике, а не отсутствие домена.

Журналы сертификатов дают имена и сведения о сертификатах. Наличие имени не подтверждает, что сайт сейчас доступен, что все имена принадлежат одной группе или что сертификат раскрывает личность оператора. Дату события в журнале фиксируй отдельно от времени получения.

Поиск соседей по IP, ASN, NS и сертификатам создаёт список совпадений для проверки. Не называй весь список одной кампанией. В общем размещении, CDN и крупных облаках на одном ресурсе могут находиться разные сайты.

К заявленной связи приложи конкретные совпадающие артефакты и их даты: идентичный сохранённый файл, одинаковая строка конфигурации, явно наблюдаемая цепочка переходов. Указывай точно, что совпало; не подменяй техническую связь идентификацией людей.

## Существующие отчёты сервисов

- **urlscan:** поиск существующих записей — `GET /api/v1/search/`; отчёт — `GET /api/v1/result/{uuid}/`. Доступные DOM и снимок относятся ко времени конкретного скана. Проверяй актуальную документацию и лимиты. Не вызывай API создания скана вместо поиска.
- **VirusTotal:** для существующего отчёта используй документированный GET соответствующего API. Веб-поиск IoC нельзя считать гарантированно пассивным: официальная документация предупреждает о сканировании и включении введённых индикаторов в набор данных. При отсутствии отчёта остановись; не отправляй URL/файл и не запускай повторное сканирование автоматически.
- **any.run и другие песочницы:** анализируй предоставленный существующий отчёт; не создавай публичное задание из персонализированной ссылки.
- Любой внешний запрос раскрывает сервису отправленный поисковый идентификатор. Не отправляй туда полный URL с личными данными или токенами. Для открытой инфраструктуры можно использовать неперсональный домен или IP в пределах задачи.

Если пользователь прямо поручил новый внешний скан, перед выполнением проверь содержимое URL и понятный пользователю режим видимости. В urlscan `unlisted` доступен некоторым исследователям и компаниям; `private` тоже не исключает передачи данных самому сервису и доступа по предоставленному идентификатору. Учитывай данное пользователем разрешение и не расширяй его.

## Сохранённый HTML и JavaScript

Читай код без исполнения. Выпиши названия полей форм, явно указанные адреса, ссылки на ресурсы и строки, связанные с имитацией бренда. Для каждого элемента укажи файл, строку или иной проверяемый фрагмент.

Различай адрес, упомянутый в коде, и сетевой запрос, наблюдавшийся в отчёте. Относительный путь не превращай в полный адрес без известной базовой страницы. Не передавай найденные секреты в IOC и общие отчёты.

Просьба страницы ввести пароль или код и наличие адреса обработки — наблюдаемые факты. Что сервер сделал с данными, какие люди за ним стоят и есть ли уязвимость у имитируемого сервиса — отдельные вопросы, на которые этих материалов может быть недостаточно. Такие выводы не делай.

## Сравнение во времени

Для повторной проверки сопоставляй одинаковые типы сведений и сохраняй обе версии. Отмечай изменение адресов, NS, статусов RDAP и новых доступных отчётов с датами. Не трактуй одно изменение DNS как доказательство блокировки или переезда оператора.

Если потерпевший сообщает о финансовом ущербе, можно включить его предоставленные документы в локальный закрытый пакет. Не запрашивай банковские секреты; юридические выводы и рекомендации по возврату денег требуют отдельной проверки актуальных официальных источников.
